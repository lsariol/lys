# Lys v0.0.0 cutover

The runbook for taking prod from today's `main` (still called "botsuite") to Lys v0.0.0: the rename, the bot's Twitch tokens moving to Cove, the first migrations, the new core and the new tables, all in one window.

**Status:** draft, not run. It grows with `release/v0.0.0`: every change that needs a prod step adds it here. A rehearsal on a copy of prod passes before the real run (Appendix A).

**Why one window.** Prod runs `main` until v0.0.0 is released; nothing from the rework reaches prod before then. So every prod change of the rework happens here, in order.

**What stays possible.** The old tables and columns are kept in v0.0.0, so the way back is today's `main` on the migrated database (see "Way back"). Dropping them is a later release.

---

## What changes in prod

| Thing | Today (`main`) | After v0.0.0 | Added by |
|---|---|---|---|
| Database, roles, schema, keys, container | `botsuite…` | `lys…` | The rename (`lys-rename.md`) |
| The bot's Twitch user tokens | `access_token` / `refresh_token` in the bot's own row of `twitch_channels` | Cove: `LYS_TWITCH_ACCESS_TOKEN`, `LYS_TWITCH_REFRESH_TOKEN` | Token work (Phase 0) |
| The Twitch app access token | Cove: `BOTSUITE_TWITCH_ACCESS_TOKEN` | Memory only, fetched at startup | Token work (Phase 0) |
| Lys's Cove token | `botsuite`, writes the access-token key | `lys`, writes both bot-token keys | Token work (Phase 0) |
| Migrations | None | On startup, as `lys_migrator` (`LYS_DATABASE_MIGRATOR_URL`) | Phase 1 |
| The notification inlet | No authentication; port 2400 published on every interface | A shared token; port not published | Phase 2 |
| Tables | Today's tables | Today's tables, untouched, plus the new ones | Phases 3 to 5 |
| Channels, prefixes, the bot account | `twitch_channels`, `twitch_settings`, `LYS_TWITCH_BOT_ID` | `platform_connections`, `connection_settings`, `bot_accounts` (the old tables are still written for rollback) | Phase 3 |
| Deploys | Every push to `main` | v0.0.0 still deploys by pushing `main`; tags from v0.0.1 | The release |

**LetterboxdWatcher is retired in the same window.** v0.0.0 polls Letterboxd itself (Phase 5), carrying on from the state LetterboxdWatcher left in `letterboxd_feed_subscriptions`, so LetterboxdWatcher is stopped in step 1 and not deployed again.

## Before the window

### 1. Code (PC)

- `release/v0.0.0` is complete: the `## v0.0.0 (YYYY-MM-DD)` section of `CHANGELOG.md` is dated, and `docker build .` passes locally (it runs the `test` stage).
- Nothing for LetterboxdWatcher: it's retired in window step 6, not updated.
- The rehearsal (Appendix A) passed.

### 2. Database roles (pgAdmin, read-only)

Migrations run as `<p>_migrator`, which acts as `<p>_owner`, so the owner has to own the schema and its tables. In `prod-rollout-plan.md` Part D these roles are still open for this project. Check on `botsuite_db`:

```sql
SELECT rolname, rolcanlogin, rolconfig FROM pg_roles WHERE rolname LIKE 'botsuite%';
SELECT nspname, pg_get_userbyid(nspowner) FROM pg_namespace WHERE nspname = 'botsuite';
SELECT tablename, tableowner FROM pg_tables WHERE schemaname = 'botsuite';
```

Expected: `botsuite_owner` (no login) owns the schema; `botsuite_migrator` has `{role=botsuite_owner}`. If the roles are missing, create them first (Part D, Admin SQL, templates in `sparkdb-schema-review.md`). Without them the first migration fails and Lys doesn't start.

Tables, sequences, types and functions owned by `Admin` instead of the owner are expected: window step 3 hands them over. The dev copy had 11 (see that step).

### 3. Cove: see what exists (server)

`docker exec -it cove /cove shell`, then `list BOTSUITE_`. The rename list in step 4 of the window must cover every key shown.

## The window

Lys is down from step 1 until step 5. LetterboxdWatcher stays down: Lys takes over its job.

### 1. Back up and stop (server)

The backup is `lys-rename.md` step 3. Then:

```bash
docker stop botsuite letterboxdwatcher
```

Stop the bot before copying its tokens: `main` writes them to the database when it shuts down.

### 2. Copy the bot's Twitch tokens (pgAdmin, on `botsuite_db`)

```sql
SELECT length(access_token), length(refresh_token)
FROM botsuite.twitch_channels WHERE user_id = '965482552';
```

Both lengths should be non-zero. Copy the two values one at a time straight into Cove in step 4. Don't paste them anywhere else, and clear the clipboard afterwards.

### 3. Rename the database (pgAdmin)

`lys-rename.md` steps 4 (the pgAdmin disconnect), 5 and 6.

Then hand everything in the `lys` schema to `lys_owner`, as `Admin` on `lys_db`. The migrator acts as `lys_owner`, so without this it can't change these objects or point foreign keys at them. Sequences tied to a table's `id` column move with their table.

1. List what isn't owned by `lys_owner`:

   ```sql
   SELECT 'schema' AS kind, nspname AS name, pg_get_userbyid(nspowner) AS owner
   FROM pg_namespace WHERE nspname = 'lys' AND pg_get_userbyid(nspowner) <> 'lys_owner'
   UNION ALL
   SELECT 'table', tablename, tableowner
   FROM pg_tables WHERE schemaname = 'lys' AND tableowner <> 'lys_owner'
   UNION ALL
   SELECT 'sequence', sequencename, sequenceowner
   FROM pg_sequences WHERE schemaname = 'lys' AND sequenceowner <> 'lys_owner'
   UNION ALL
   SELECT 'type', t.typname, pg_get_userbyid(t.typowner)
   FROM pg_type t JOIN pg_namespace n ON n.oid = t.typnamespace
   WHERE n.nspname = 'lys' AND t.typtype IN ('e', 'd') AND pg_get_userbyid(t.typowner) <> 'lys_owner'
   UNION ALL
   SELECT 'function', p.proname, pg_get_userbyid(p.proowner)
   FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
   WHERE n.nspname = 'lys' AND pg_get_userbyid(p.proowner) <> 'lys_owner'
   ORDER BY 1, 2;
   ```

   On the dev copy this listed 11 rows: the six tables below, their three sequences, the `request_status` type and the `log_twitch_channel_changes` function.

2. Hand them over:

   ```sql
   BEGIN;
   ALTER TABLE lys.feature_requests OWNER TO lys_owner;
   ALTER TABLE lys.game_events OWNER TO lys_owner;
   ALTER TABLE lys.letterboxd_feed_subscriptions OWNER TO lys_owner;
   ALTER TABLE lys.sleeper_connections OWNER TO lys_owner;
   ALTER TABLE lys.sleeper_events OWNER TO lys_owner;
   ALTER TABLE lys.sleeper_leagues OWNER TO lys_owner;
   ALTER TYPE lys.request_status OWNER TO lys_owner;
   ALTER FUNCTION lys.log_twitch_channel_changes() OWNER TO lys_owner;
   COMMIT;
   ```

   If step 1 listed anything else, add an `ALTER … OWNER TO lys_owner` line for it. The existing grants to `lys_app` and `lys_reader` carry over.

3. Run step 1 again: it should return no rows.

### 4. Cove (server, `cove shell`)

1. The key renames from `lys-rename.md` step 7.
2. Lys's new token, writing both bot-token keys:
   ```
   token create lys --allow 'LYS_*' --write LYS_TWITCH_ACCESS_TOKEN --write LYS_TWITCH_REFRESH_TOKEN
   create LYS_COVE_TOKEN <the token it just printed>
   ```
3. The bot's tokens. The renamed `LYS_TWITCH_ACCESS_TOKEN` holds the old *app* token; replace it with the bot's user token:
   ```
   update LYS_TWITCH_ACCESS_TOKEN <the access_token from step 2>
   create LYS_TWITCH_REFRESH_TOKEN <the refresh_token from step 2>
   ```
4. The database URLs (same passwords as before):
   ```
   update LYS_DATABASE_URL postgres://lys_app:<password>@sparkdb:5432/lys_db?sslmode=disable
   create LYS_DATABASE_MIGRATOR_URL postgres://lys_migrator:<password>@sparkdb:5432/lys_db?sslmode=disable
   ```
5. The inlet token, for services that post to Lys (none once LetterboxdWatcher is retired; the website's enrollment will be one). Lighthouse passes it to Lys as `SHARED_LYS_NOTIFICATION_TOKEN`; a sender puts it in `Authorization: Bearer <token>`:
   ```
   generate SHARED_LYS_NOTIFICATION_TOKEN 64
   ```
   The inlet's address is `http://lys:2400/notifications`: the port is no longer published on the server, so only the `spark` network reaches it.
6. Whatever later phases add (the list under "Phase notes").

**Check:** `token show lys` reaches every `LYS_` key and writes the two token keys.

### 5. Lighthouse and the deploy (server, then PC)

1. **Server:** `lh list` shows what Lighthouse calls Lys. If it's `botsuite`, run `lh rename botsuite lys`.
2. **Server:** `docker rm -f botsuite`. The new `lys` container needs its port and name.
3. **PC:** fast-forward `release/v0.0.0` into `main` and push `main`. Lighthouse deploys it.
4. **Server:** `docker logs -f lys`. Expect the migrations to be applied (or "database is up to date"), then the Twitch connection and channel joins.

### 6. Retire LetterboxdWatcher (server)

It has been stopped since step 1. After Lys's first Letterboxd poll (`docker logs lys`) has run without errors:

```bash
lh remove letterboxdwatcher
```

That stops Lighthouse watching it and removes its container; its images and data stay. Later: revoke its Cove token and archive its repository.

### 7. Check

- `docker ps` shows `lys` healthy, and neither `botsuite` nor `letterboxdwatcher`.
- The bot answers in a channel, and a command that uses the database works (`!request …`, `!oneup stats`).
- `lys migrate status` (with `docker exec lys /lys migrate status`) lists every migration as applied.
- `docker exec lys /lys channel list` lists every channel prod had, as active, with its prefix. The count matches `SELECT count(*) FROM lys.twitch_channels WHERE active AND NOT banned` (pgAdmin) for the active ones.
- After Lys's first token refresh, `history LYS_TWITCH_REFRESH_TOKEN` in Cove shows `lys` as the writer, and there's no `403 forbidden_key` in `docker logs lys`.
- A new Letterboxd review from a watched account shows up in its channel (Lys's own poller now).
- A request to the inlet without the token is refused: `docker run --rm --network spark alpine wget -qO- --post-data '{}' http://lys:2400/notifications` prints a 401 error.
- `curl -s http://<server>:2400/health` from the PC fails to connect: the port isn't published any more.

### 8. Tag (PC)

```powershell
git tag v0.0.0 <the main commit>
git push origin v0.0.0
```

This tag is the baseline for tag deploys (see "After").

## After

- Log the cutover in `prod-rollout-plan.md` (Appendix B).
- `pending-work.md`: close the mobasity-web "Lys shows as botsuite" entry, and the "lys, marquee" port entry for Lys.
- Cove: `token revoke botsuite`, `delete BOTSUITE_COVE_TOKEN`.
- Delete the backups after a few days (`lys-rename.md` step 9).
- **PC:** once `docker exec -it lys /lys bot authorize` has worked once (the next time the bot needs re-authorizing, or as a test), delete `notes/NewUserFlow.txt`: it holds the Twitch client secrets the CLI replaces.
- **v0.0.1:** `x-lighthouse: {deploy: releases}`, the `lighthouse-publisher` App on the repo, rulesets for `main` and `v*`. Then `lh publish lys v0.0.0` gives v0.0.0 its GitHub Release (as the baseline it's never published automatically).
- **A later release:** drop the old tables and columns, including the token columns in `twitch_channels`.

## Way back

1. **Server:** `docker stop lys`, then `docker rm lys`.
2. **pgAdmin:** reverse the rename (`lys-rename.md` "Way back"). The migrations only added tables and columns, so today's `main` runs on the result.
3. **Cove:** rename the keys back. `main` reads the bot's tokens from the database. If Twitch changed the refresh token since the window, copy the one in `LYS_TWITCH_REFRESH_TOKEN` back into the bot's row before renaming.
4. **PC:** redeploy the previous `main` commit.
5. **Server:** start LetterboxdWatcher again: `docker start letterboxdwatcher` if its container is still there, otherwise re-add it to Lighthouse (`lh add <its repo URL>`). It picks up from `letterboxd_feed_subscriptions`, which v0.0.0 kept current.

**What's lost:** nothing that matters. Channels, prefixes, blocks, games, requests, Sleeper links and Letterboxd subscriptions were all also written to the old tables, which today's `main` reads. A roll forward later links anything the old release added in the meantime (Lys does it on every start).

**Last resort:** restore the step 1 backup.

## Phase notes

Each phase adds its prod steps above and a line here.

- **Phase 0, tokens:** the app token stays in memory. The bot's user tokens go in Cove under their own keys (window step 4). At startup Lys refreshes them, writes the new pair back, and refuses to start if they belong to another account than `LYS_TWITCH_BOT_ID`, so copying the wrong row's tokens fails loudly. `LYS_TWITCH_BOT_NAME` is no longer read (it was unused).
- **Phase 1, migrations:** Lys migrates on startup when `LYS_DATABASE_MIGRATOR_URL` is in Cove (without it, it logs a warning and skips them), then checks the schema version as `lys_app` and refuses to start if it's behind. The baseline `00001` creates only what's missing, so on prod it changes nothing; it only adds `USAGE` on the schema, the default privileges for new tables, and read access to goose's version table, if any are missing. Tested on a copy of the dev database (schema and row counts unchanged) and on an empty one (the schema it builds matches prod's exactly). Needs the `citext` extension in `lys_db`, and `lys_migrator` with `role=lys_owner` (before-the-window step 2), so goose's table belongs to the owner. The first deploy logs `migration: OK up 00001_baseline.sql`; later ones log `migration: database is up to date`.
- **Phase 2, new core:** the inlet now refuses requests without `Authorization: Bearer <SHARED_LYS_NOTIFICATION_TOKEN>` (an empty token refuses everything, and Lys logs a warning at startup), and port 2400 is only exposed on the `spark` network. `/health` answers 503 while Twitch is disconnected, so Docker marks Lys unhealthy instead of healthy-but-deaf. The bot ignores its own chat messages.
- **Phase 3, identity tables:** migration `00002` copies every `twitch_channels` row into a community and a connection, with its prefix and its revoked or banned state; the bot's own channel stays a channel it joins. Broadcaster tokens aren't copied. Every user the feature tables mention becomes a `platform_users` row. On the dev copy: 2 channels became 2 connections with matching prefixes, 22 users were copied, and the schema came out identical to a fresh build. `bot_accounts` gets its row on the first start, from `LYS_TWITCH_BOT_ID` once Twitch confirms the token; after that the key is only a fallback. Channel and prefix changes still write `twitch_channels` and `twitch_settings`, so the way back keeps them. Adding a channel is `lys channel add <login>` plus a restart (`lys help new-channel`).
- **Phase 4, feature data:** migration `00003` adds `connection_id`/`platform_user_id` (and `community_id` for Sleeper leagues) to the feature tables, and `feed_subscriptions`. Lys fills them on every start, touching only unlinked rows, so rows the old `main` writes after a rollback get linked on the way forward. Channels the data mentions without a `twitch_channels` row get a connection that isn't authorized: Lys doesn't join them, and `lys channel list` shows them as `revoked`. On the dev copy every row linked (917 game events, 85 requests, both leagues, 15 Letterboxd subscriptions into feeds). Commands read only the new columns; the old ones are still written. Decision: Lys absorbs LetterboxdWatcher (Phase 5), so it's retired in this window.
- **Phase 5, scheduler and feeds:** the Letterboxd poller must also write its polling state (`last_seen_guid`, `last_alerted_at`) back to `letterboxd_feed_subscriptions`, so a rollback's LetterboxdWatcher doesn't announce old reviews again.

## Appendix A: Rehearsal (PC, before the window)

1. **Server:** dump prod's database, as in `lys-rename.md` step 3, and copy the file to the PC **outside any repository** (it contains the bot's and broadcasters' tokens).
2. **PC:** restore it into the dev Postgres (`sparkdb-dev`) as a scratch database, run the rename SQL from window step 3 on it, and point a local Lys from `release/v0.0.0` at it with a migrator URL.
3. **Check:** the migrations apply; the new tables' row counts match the old ones; `lys migrate status` lists everything as applied; a second start changes nothing. For the schema itself: `go test ./internal/database -run TestMigrations` with `LYS_TEST_MIGRATOR_DATABASE_URL` and `LYS_TEST_DATABASE_URL` pointing at the scratch database passes when, after migrating, it matches `internal/database/testdata/schema.txt`.
4. Drop the scratch database and delete the dump file.
