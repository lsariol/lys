# Lys v0.0.0 cutover

The runbook for taking prod from today's `main` (still called "botsuite") to Lys v0.0.0: the rename, the bot's Twitch tokens moving to Cove, the first migrations, the new core and the new tables, all in one window.

**Status:** draft, not run. It grows with `release/v0.0.0`: every change that needs a prod step adds it here. A rehearsal on a copy of prod passes before the real run (Appendix A).

**Why one window.** Prod runs `main` until v0.0.0 is released; nothing from the rework reaches prod before then. So every prod change of the rework happens here, in order.

**What stays possible.** The old tables and columns are kept in v0.0.0, so the way back is today's `main` on the migrated database (see "Way back"). Dropping them is a later release.

---

## What changes in prod

| Thing | Today (`main`) | After v0.0.0 | Added by |
|---|---|---|---|
| Database, roles, schema, keys, container | `botsuite…` | `lys…` | The rename (`lys-rename.md`) |
| The bot's Twitch user tokens | `access_token` / `refresh_token` in the bot's own row of `twitch_channels` | Cove: `LYS_TWITCH_ACCESS_TOKEN`, `LYS_TWITCH_REFRESH_TOKEN` | Token work (Phase 0) |
| The Twitch app access token | Cove: `BOTSUITE_TWITCH_ACCESS_TOKEN` | Memory only, fetched at startup | Token work (Phase 0) |
| Lys's Cove token | `botsuite`, writes the access-token key | `lys`, writes both bot-token keys | Token work (Phase 0) |
| Migrations | None | On startup, as `lys_migrator` (`LYS_DATABASE_MIGRATOR_URL`) | Phase 1 |
| The notification inlet | No authentication; port 2400 published on every interface | A shared token; port not published | Phase 2 |
| Tables | Today's tables | Today's tables, untouched, plus the new ones | Phases 3 to 5 |
| Channels, prefixes, the bot account | `twitch_channels`, `twitch_settings`, `LYS_TWITCH_BOT_ID` | `platform_connections`, `connection_settings`, `bot_accounts` (the old tables are still written for rollback) | Phase 3 |
| Deploys | Every push to `main` | v0.0.0 still deploys by pushing `main`; tags from v0.0.1 | The release |

**LetterboxdWatcher is retired in the same window.** v0.0.0 polls Letterboxd itself (Phase 5), carrying on from the state LetterboxdWatcher left in `letterboxd_feed_subscriptions`, so LetterboxdWatcher is stopped in step 2 and not deployed again.

## The window

About 45 minutes. The bot is offline from step 2 until step 9. Every step says where it runs, what success looks like, and what to do if it doesn't; **"Way back"** below says how to undo everything done up to any step.

Three rules for the whole window:
- **Stop with `lh stop`, never `docker stop`.** Lighthouse's reconcile loop starts any project again that's been down for two minutes, unless it was stopped through Lighthouse. A `docker stop botsuite` would bring the old bot back in the middle of the rename.
- **Nothing deploys by itself.** Once `lys` is stopped through Lighthouse, pushing `main` doesn't deploy it; only `lh deploy lys` in step 9 does.
- **Secrets go straight from where they are to `cove shell`.** Never into a file, a chat, or pgAdmin's Query Tool (it keeps every query in its history). Clear the clipboard when done.

### 4. Rename the database, roles and schema (pgAdmin)

**4a. Query Tool on `AdminDB`** (not `botsuite_db`; the tab title says which). Run the whole block:


- **Success:** "Query returned successfully". Refresh the server in the tree: it shows `lys_db`.
- `current database cannot be renamed`: the Query Tool is on `botsuite_db`; open one on `AdminDB`.
- `is being accessed by other users`: something is still connected (another pgAdmin tab, or an app that didn't stop); check step 2 and run the block again. Nothing was renamed if this fails.

**4b. Query Tool on `lys_db`.** Rename the schema and point the two trigger functions at it:

```sql
ALTER SCHEMA botsuite RENAME TO lys;

DO $$
DECLARE
  f   oid;
  def text;
BEGIN
  FOR f IN
    SELECT p.oid
    FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
    WHERE n.nspname = 'lys' AND p.prokind = 'f'
  LOOP
    def := pg_get_functiondef(f);
    IF def LIKE '%botsuite.%' THEN
      EXECUTE replace(def, 'botsuite.', 'lys.');
    END IF;
  END LOOP;
END $$;

SELECT count(*) AS still_naming_botsuite
FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'lys' AND p.prokind = 'f' AND pg_get_functiondef(p.oid) LIKE '%botsuite.%';

SELECT rolname, rolconfig FROM pg_roles WHERE rolname LIKE 'lys%' OR rolname LIKE 'botsuite%';
```

- **Success:** `still_naming_botsuite` is `0`; the roles are the four `lys_` ones, `lys_migrator` with `{role=lys_owner}`, and no `botsuite_` ones.

### 5. Hand everything to `lys_owner` (pgAdmin, Query Tool on `lys_db`)

The migrator acts as `lys_owner`, so it has to own the database and every object in the schema. Without the database, Lys's first step fails with `permission denied for database lys_db`.

**5a. List what `lys_owner` doesn't own:**

```sql
SELECT 'database' AS kind, datname AS name, pg_get_userbyid(datdba) AS owner
FROM pg_database WHERE datname = 'lys_db' AND pg_get_userbyid(datdba) <> 'lys_owner'
UNION ALL
SELECT 'schema', nspname, pg_get_userbyid(nspowner)
FROM pg_namespace WHERE nspname = 'lys' AND pg_get_userbyid(nspowner) <> 'lys_owner'
UNION ALL
SELECT 'table', tablename, tableowner
FROM pg_tables WHERE schemaname = 'lys' AND tableowner <> 'lys_owner'
UNION ALL
SELECT 'sequence', sequencename, sequenceowner
FROM pg_sequences WHERE schemaname = 'lys' AND sequenceowner <> 'lys_owner'
UNION ALL
SELECT 'type', t.typname, pg_get_userbyid(t.typowner)
FROM pg_type t JOIN pg_namespace n ON n.oid = t.typnamespace
WHERE n.nspname = 'lys' AND t.typtype IN ('e', 'd') AND pg_get_userbyid(t.typowner) <> 'lys_owner'
UNION ALL
SELECT 'function', p.proname, pg_get_userbyid(p.proowner)
FROM pg_proc p JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'lys' AND pg_get_userbyid(p.proowner) <> 'lys_owner'
```

## After

- Log the cutover in `prod-rollout-plan.md` (Appendix B).
- `pending-work.md`: close the mobasity-web "Lys shows as botsuite" entry, and the "lys, marquee" port entry for Lys.
- Cove: `token revoke botsuite`, `delete BOTSUITE_COVE_TOKEN`, and the keys the window left for the way back: `BOTSUITE_NOTIFICATION_URL`, `BOTSUITE_APP_PASSWORD`, `BOTSUITE_OWNER_PASSWORD`, `BOTSUITE_READER_PASSWORD`.
- Delete the backups after a few days: `sudo rm /srv/backups/*-before-lys*`.
- Once the way back is off the table: `docker rm botsuite`, the old container, stopped since step 2 (the way back redeploys it anyway).
- **PC:** once `docker exec -it lys /lys bot authorize` has worked once (the next time the bot needs re-authorizing, or as a test), delete `notes/NewUserFlow.txt`: it holds the Twitch client secrets the CLI replaces.
- **v0.0.1:** `x-lighthouse: {deploy: releases}`, the `lighthouse-publisher` App on the repo, rulesets for `main` and `v*`. Then `lh publish lys v0.0.0` gives v0.0.0 its GitHub Release (as the baseline it's never published automatically).
- **Removing the rollback copies (two releases, so each can still roll back to the one before):**
  1. *Once v0.0.0 has run in prod for a few weeks and going back to the old `main` is off the table:* a code-only release stops writing and reading the old tables and columns (the "rollback copy" writes in `connections`, `letterboxd`, `oneuppuzzle`, `request` and `sleeper`, and the Letterboxd poller's copy of its state) and takes `LinkLegacyRows` out of startup (which also ends its full scans of `game_events` on every start). Rolling back to v0.0.0 still works: the tables are still there. The OneUp puzzle queries are rewritten here anyway, so fix the puzzle-number one in the same release: it reads `(details->'puzzle_id')::INT`, which no index matches, and scans the whole table (140 ms at 500,000 results). Write it with `->>` and add an index on `((details->>'puzzle_id')::int), ((details->>'time_seconds')::int)` for unflagged OneUp rows, plus one on `platform_users (platform, lower(display_name))` for stats by name.
  2. *The release after that:* a migration drops `twitch_channels`, `twitch_settings`, `twitch_channel_events`, `letterboxd_feed_subscriptions`, their triggers and functions, and the old text ID and name columns in `game_events`, `feature_requests` and the Sleeper tables; the bot tokens left in `twitch_channels` go with them. The new key columns (`connection_id`, `platform_user_id`, `community_id`) become `NOT NULL`.
- **Later:** send faster where the bot is a moderator, VIP or broadcaster. Twitch allows them 100 messages per 30 seconds instead of 20, and exempts them from slow mode; Lys spaces every channel's messages 1.5 s apart today. It can learn its role in each channel from the badges on its own messages, which EventSub already delivers. **Build it together with one account-wide limiter:** Twitch's limits are per account across all channels (20 per 30 s when not a mod; going over makes Twitch ignore the bot for an hour), but Lys only spaces messages per channel, so faster per-channel sending alone makes going over more likely. First log Helix's `Ratelimit-Limit` and `Ratelimit-Remaining` for a few days: the Send Chat Message API has its own bucket, and its size decides how urgent this is. Replies go before announcements and autoposts.
- **Later, before the website dashboard:** per-channel command settings, so a community owner can turn each command on or off and choose who may use it (everyone, moderators, or the owner). Each command declares its default tier in its `Spec`, and the router enforces it, instead of each command checking roles itself; a table keyed by connection and command holds the channel's overrides, cached like the prefix. Commands with owner-only subcommands (`!ff link league`, `!ff alerts`) need a tier per subcommand. Add a concurrency cap and cooldowns to `Spec` in the same change (e.g. `!gpt` 2 at a time), so slow commands can't take every worker (see the performance item below).
- **Performance (measured 2026-10-28; numbers and details in `notes/performance-review.md`):**
  - *First:* slow commands stall all of chat. The 8 workers handle every message, so 8 commands waiting on an API (`!gpt` up to 30 s) hold up everything, plain chat and the autoposts' activity count included (3 s behind a 3 s API in the test). If it lasts, the EventSub read loop stops reading, Twitch disconnects Lys for missed pings, and every channel is rejoined. Fix: observers and matching off the workers, a concurrency cap for slow commands (with the command settings above), and an EventSub reader that drops and counts messages instead of blocking.
  - *The join path, in one change:* channels are joined one Helix call at a time, holding the channel lock, before the read loop starts (on a reconnect, inside it): 1.4 s for 9 channels, 15 s for 100, 45 s for 300. Start reading first, subscribe about 8 at a time, and take the lock only to record results. Past 300 channels, shard across connections (Twitch allows 300 subscriptions per WebSocket, 3 WebSockets) or use conduits. In the same change: refresh the bot's token only when it's close to expiring or on a 401, not on every join and twice at startup; each refresh is a Twitch call plus two Cove writes and two new Cove history versions.
  - *Compose file:* every chat message goes to the container log, and no `logging:` options cap it. Add `json-file` with `max-size: "10m"`, `max-file: "5"`, or log only commands.
  - *As channels and feeds grow:* the Letterboxd poller checks one subscription at a time at least 5 s apart, so past 300 a round outgrows its 25 minutes (1,000 take 83), and a feed followed in several channels is fetched once per channel. Fetch each feed once per round, use conditional GETs, and a few at a time. Set the database pool size explicitly (pgxpool defaults to the larger of 4 and the CPU count, and the change listener holds one connection).
  - *Only if it ever matters:* reminders run up to 5 s late (the scheduler checks every 5 s).
- **When moderation features are added:** add their `moderator:*` scopes to the bot's `BotScopes` (then `lys bot authorize` again), and ask for any `channel:*` scopes they need in the website's onboarding flow.

## Way back

Undo only what was done, newest first. Each part says which window step it reverses. The old bot (`aea12c3`) runs on the renamed-back database as it is: the migrations only added tables and columns, and the ownership and grant changes in step 5 don't affect it.

**Stopped before step 4 (nothing renamed yet):** `lh start botsuite`, `lh start letterboxdwatcher`. Done.

Otherwise, in this order:

1. **If step 9 ran** (server): `lh stop lys`, then `docker ps -a --filter name=lys --filter name=botsuite` and `docker stop` anything still running.    The old bot fetches a new app token at startup and writes it over `BOTSUITE_TWITCH_ACCESS_TOKEN`, so the user token in it doesn't matter. ## Phase notes

Each phase adds its prod steps above and a line here.

- **Phase 0, tokens:** the app token stays in memory. The bot's user tokens go in Cove under their own keys (window step 6). At startup Lys refreshes them, writes the new pair back, and refuses to start if they belong to another account than `LYS_TWITCH_BOT_ID`, so copying the wrong row's tokens fails loudly. `LYS_TWITCH_BOT_NAME` is no longer read (it was unused).
- **Phase 1, migrations:** Lys migrates on startup when `LYS_DATABASE_MIGRATOR_URL` is in Cove (without it, it logs a warning and skips them), then checks the schema version as `lys_app` and refuses to start if it's behind. The baseline `00001` creates only what's missing, so on prod it changes nothing; it only adds `USAGE` on the schema, the default privileges for new tables, and read access to goose's version table, if any are missing. Tested on a copy of the dev database (schema and row counts unchanged) and on an empty one (the schema it builds matches prod's exactly). Needs the `citext` extension in `lys_db`, and `lys_migrator` with `role=lys_owner` (before-the-window step 2), so goose's table belongs to the owner. The first deploy logs `migration: OK up 00001_baseline.sql`; later ones log `migration: database is up to date`.
- **Phase 2, new core:** the inlet now refuses requests without `Authorization: Bearer <SHARED_LYS_NOTIFICATION_TOKEN>` (an empty token refuses everything, and Lys logs a warning at startup), and port 2400 is only exposed on the `spark` network. `/health` answers 503 while Twitch is disconnected, so Docker marks Lys unhealthy instead of healthy-but-deaf. The bot ignores its own chat messages.
- **Phase 3, identity tables:** migration `00002` copies every `twitch_channels` row into a community and a connection, with its prefix and its revoked or banned state; the bot's own channel stays a channel it joins. Broadcaster tokens aren't copied. Every user the feature tables mention becomes a `platform_users` row. On the dev copy: 2 channels became 2 connections with matching prefixes, 22 users were copied, and the schema came out identical to a fresh build. `bot_accounts` gets its row on the first start, from `LYS_TWITCH_BOT_ID` once Twitch confirms the token; after that the key is only a fallback. Channel and prefix changes still write `twitch_channels` and `twitch_settings`, so the way back keeps them. Adding a channel is `lys channel add <login>` plus a restart (`lys help new-channel`).
- **Phase 4, feature data:** migration `00003` adds `connection_id`/`platform_user_id` (and `community_id` for Sleeper leagues) to the feature tables, and `feed_subscriptions`. Lys fills them on every start, touching only unlinked rows, so rows the old `main` writes after a rollback get linked on the way forward. Channels the data mentions without a `twitch_channels` row get a connection that isn't authorized: Lys doesn't join them, and `lys channel list` shows them as `revoked`. On the dev copy every row linked (917 game events, 85 requests, both leagues, 15 Letterboxd subscriptions into feeds). Commands read only the new columns; the old ones are still written. Decision: Lys absorbs LetterboxdWatcher (Phase 5), so it's retired in this window.
- **Enrollment API (before release):** `POST /channels` (`{"platform", "channel_id"}`) enrolls a channel and the running bot joins it within seconds. Lys looks the ID up on Twitch first and takes the name and login from there; an ID Twitch doesn't know is refused with a 400, and Twitch being unreachable with a 502. The answer gives the channel's name and says whether it's new, active, or blocked by Lys. When Twitch has given a name to a new channel that an older row in `twitch_channels` still holds (a rename), the older row's name becomes `<name>~<id>`: that rollback copy allows one row per name. `DELETE /channels/{platform}/{id}` is the owner turning Lys off: Lys leaves, and the channel's settings and history stay. Both need `SHARED_LYS_ENROLLMENT_TOKEN`; without it set, every request is refused. The website verifies the owner (OAuth) before calling.
- **EventSub handling (before release):** a silent connection is reopened after its keepalive timeout plus 5 seconds. A ban (`chat_user_banned`) or a deleted account (`user_removed`) marks that channel revoked and Lys leaves it; `authorization_revoked` means the bot account's own grant is gone, so `/health` goes unhealthy and `docker logs lys` says to run `lys bot authorize`. Sends that Twitch refuses pause that channel for 10 minutes. Check after deploy: no `[EventSub] connection lost` lines repeating in `docker logs lys`.
- **Phase 5, scheduler and feeds:** migration `00004` adds `scheduled_jobs` (reminders, autoposts). The Letterboxd poller replaces LetterboxdWatcher and writes its polling state to both `feed_subscriptions` and `letterboxd_feed_subscriptions`, so a rollback's LetterboxdWatcher doesn't announce old reviews again. The Sleeper poller's first check of each league records existing trades and waivers without announcing them, so prod's league doesn't get the season replayed; after that, `docker logs lys` shows `[Sleeper]` lines only for errors. Channel changes reach the running bot through Postgres `LISTEN`/`NOTIFY`, so `lys channel add/block/unblock` work without a restart; `lys_app` needs nothing extra for that.
