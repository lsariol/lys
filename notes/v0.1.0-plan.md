## 1. Tag deploys

From v0.1.0 on, pushing `main` deploys nothing; pushing a `v*` tag whose commit is on `main` does (Lighthouse §4.7, §7.2).

**Before the release (once, by hand):**
1. GitHub: rename the repository to `lsariol/lys` if not done yet, then `lh set-url lys https://github.com/lsariol/lys` and `lh check lys`.
2. GitHub: install the `lighthouse-publisher` App on the repository (selected repositories only).
3. GitHub: rulesets protecting `main` and `v*` tags (no force-push, no deletion), with no bypass for the App.
4. Server: `lh publish lys v0.0.0`, so v0.0.0 gets its GitHub Release from the CHANGELOG in its tagged commit (as the baseline it's never published automatically).

**In the code:** `x-lighthouse: {deploy: releases}` at the top of `docker-compose.yaml`, in the release's last commit.

**Release flow (from `~/.claude/CLAUDE.md`):** CHANGELOG section `## v0.1.0 (date)` in the commit that gets tagged, fast-forward `main`, push `main` (nothing deploys: Lighthouse reads the new `x-lighthouse` from `main` and switches to releases), then tag `v0.1.0` and push the tag (it deploys, and Lighthouse publishes the Release after the checks pass). `lh list` then shows `tags` for `lys`.

**Way back:** `lh deploy lys v0.0.0`. In releases mode a deploy by hand sticks until a newer tag. v0.0.0 runs on v0.1.0's database (§2's migration is additive).

## 2. Debloat

### 2a. Stop writing the rollback copies (code)

v0.0.0 writes every change twice, to the new tables and to the old ones, so today's old `main` could take over. That's no longer needed: the way back from v0.1.0 is v0.0.0, which reads only the new tables.

The state write isn't needed: v0.0.0 only takes a newer one |
| `internal/commands/cmds/oneuppuzzle`, `request` | the old text columns (`user_id`, `username`, `channel_id`, `channel_name`) in inserts |

## 3. Command permissions, cooldowns, concurrency

Today each command checks roles itself (`IsChannelOwner`, `HasPrivilege`, `RoleModerator`), with a bot-owner override in some. v0.1.0 moves this into the command's `Spec`, enforced by the router, so a new command declares who may use it in one field.

**Decided 2026-10-28:** per-channel overrides (an owner turning a command off, or changing who may use it) and any screen to edit them wait for the website. v0.1.0 builds the enforcement and the defaults; the overrides table and its API come with the dashboard.

- **`Spec.Access`**: `Everyone` (default), `VIP`, `Moderator`, `Owner`. A higher role passes a lower tier (the owner passes `Moderator`). The router checks it before running the command, and replies "Only the channel's owner can use !settings." (or moderators) when it fails.
- **Subcommands:** `Spec.Sub map[string]Access` for the first argument, e.g. `!ff` is `Everyone`, with `link`, `unlink` `Owner`. Rules finer than that (`!ff alerts` reads for everyone, changes for the owner) use one shared helper, `req.Allowed(commands.Owner)`, instead of each command's own check.
- **`Spec.Cooldown`** per channel, and **`Spec.UserCooldown`** per person, for expensive commands (`!gpt`, `!catfact`, `!randomdog`). A command in its cooldown is ignored quietly, or once per cooldown says "!gpt is cooling down (12 s)".
- **`Spec.Concurrency`**: how many may run at once across all channels (e.g. `!gpt` 2). Past it, "Busy, try again in a moment." This is what stops slow commands taking every worker (performance review #1, §6).
- **Migrating the commands:** `autopost` (`Moderator`), `settings prefix set`, `ff link/unlink/alerts`, `request` admin actions. Their own checks go.
- **Decision to make while building it:** does the bot's owner keep an override in other people's channels? Recommended: no, as for autoposts. `Owner` means the channel's owner; your own fixes go through the `lys` CLI (`lys channel prefix <channel> <prefix>` would be the one to add). `request`'s admin actions stay yours through a separate `BotOwner` tier.
- `!help <command>` shows who may use it.

## 4. Faster sending as moderator, VIP or broadcaster

Twitch's chat limits are per account across all channels: 20 messages per 30 s in channels where the bot isn't privileged, 100 per 30 s overall where it's a moderator, VIP or broadcaster, and 1 per second in a channel where it isn't. Going over makes Twitch ignore the bot for an hour. Lys only spaces messages 1.5 s apart per channel today, with nothing across channels.

1. **Know the bot's role per channel.** The bot's own messages arrive through EventSub with its badges, and `bot/io.go` already drops them; read their badges first. Store the result in `twitch_connection_details.bot_is_moderator` (it exists, nothing writes it yet), so a restart starts from the last known role. Until the bot has spoken in a channel, it's treated as not privileged.
2. **One account-wide limiter** in front of the per-channel queues: a 100/30 s bucket for everything, and a 20/30 s bucket for channels where the bot isn't privileged. Sized from v0.0.1's logs; if Helix's own bucket (`Ratelimit-Limit`) turns out smaller, its headers win.
3. **Per channel:** 1 s apart where not privileged (and slower in slow mode, if Twitch reports it), about 0.3 s where privileged.
4. **Priority across channels:** replies, then announcements (Sleeper, Letterboxd), then autoposts. `core.Outbound` gets a `Kind`. When the account limit is reached, autoposts wait first.
5. **Tests** with a fake clock: 120 messages over 10 channels never exceed either bucket; a reply jumps ahead of a queue of autoposts.

No new scopes are needed.

## 5. Sleeper as a source, with lineup reminders

### 5a. Move the poller

The trades and waivers poller lives in `internal/commands/cmds/sleeper` today. Split it like Letterboxd: the Sleeper API client and the league store go to `internal/features/sleeper` (the folder exists, empty), the chat command stays in `internal/commands/cmds/sleeper`, and the poller becomes `internal/sources/sleeper`. Both use the feature package; neither imports the other. One client is built in `main` and shared, so the player catalog is downloaded and kept once. Letterboxd needs no such split: its command only checks a feed exists and its poller does the reading, so they share a table, not code (checked 2026-10-28).

### 5b. Lineup reminders

**Decided 2026-10-28:** three reminders a week, in each league's channels, during the NFL regular season:

| When | Example |
|---|---|
| 1 day before the week's first game (usually Thursday night) | 🏈 Week 9 starts in 1 day: JAX @ BAL, Thu 8:15 PM ET. Set your lineups! |
| 1 hour before it | 🏈 1 hour until JAX @ BAL (8:15 PM ET): Thursday players lock then. Set your lineups! |
| 1 hour before Sunday's first game | 🏈 1 hour until Sunday's first game: CIN vs ATL, 9:30 AM ET. Set your lineups! |

When the week's first game is on Sunday, the first two reminders are the only ones (no duplicate hour). Each reminder is sent once per league, kickoff and offset.

- **Kickoff times:** Sleeper's schedule (`api.sleeper.app/schedule/nfl/regular/<season>`) has dates only. ESPN's public scoreboard has the times: `site.api.espn.com/apis/site/v2/sports/football/nfl/scoreboard?seasontype=2&week=<n>&dates=<season>` (checked 2026-10-28: week 9's 15 games, first `2026-11-06T01:15Z`). It's unofficial, so: one request per week cached for 6 hours, a test against a saved response, and if it fails or changes, a logged `[Sleeper]` error and no reminder (never a wrong one).
- **Which week:** Sleeper's `state/nfl` (`week`, `season_type`), as the poller uses today. Only `regular`: fantasy playoffs end inside the regular season.
- **Timing:** the source sleeps until the next reminder is due (at most 10 minutes, so new leagues and changed kickoffs are picked up), and sends a reminder only within 30 minutes after its time, so a restart never sends a stale "1 day" alert a few hours before kickoff.
- **No new table:** each sent reminder is a `sleeper_events` row (`event_type 'lineup_reminder'`, `external_event_id` like `2026-w9-<kickoff unix time>-1h`), whose unique key already stops duplicates across restarts and instances.
- **Toggle:** `!ff alerts lineups on|off`, next to trades and waivers. On by default.
- **Times are Eastern** (`America/New_York`), as the NFL lists them. The image is Alpine without time zones, so the binary imports `time/tzdata`.
- **Tests:** a fixed schedule and a fake clock: three reminders in a Thursday week, two in a Sunday-first week, none outside the season, none after a restart past the 30-minute window, none twice.

## 6. Performance

From `notes/performance-review.md` (measured 2026-10-28), in its order:

1. **Chat never stalls behind slow commands.** Observers (activity tracker, puzzle matching) and command lookup run as the message arrives; only the command itself takes a worker; §3's concurrency caps keep slow commands to a few workers. The EventSub reader never blocks: when its buffer is full it drops the message and counts it (logged once a minute), so it keeps answering Twitch's pings.
2. **Joins:** subscribe about 8 at a time, take the channel lock only to record each result. (Done 2026-10-28. Reading the socket before joining was left out: at 8 at a time even 300 channels join in about 6 s, well inside Twitch's 10 s, and reading first would race with reconnects over the session.) Refresh the bot's token only when less than 10 minutes remain or on a 401 (not on every join, twice at startup), and write to Cove only when the token changed.
3. **Letterboxd:** fetch each feed URL once per round for every channel that follows it; conditional requests (`If-None-Match`, `If-Modified-Since`); 4 fetches at a time with a polite gap.
4. **Database pool:** set `pool_max_conns` explicitly (12) instead of the CPU-dependent default.
5. **Command timing:** one log line per command with its total time (message timestamp → reply accepted by Helix), the measurement the review couldn't make.
6. Not now: past 300 channels (sharding or conduits), the scheduler's 5 s tick.

## 7. `lys shell`

`~/.claude/CLAUDE.md`'s CLI standard asks for an interactive shell; Lys has only one-off commands. `docker exec -it lys /lys shell` opens it: line editing, history in memory, Tab completion from the command table (its `Complete` functions exist already), the prompt `lys (prod)>` in red in prod. Then the server alias `alias lys='docker exec -it lys /lys shell'`, and the runbooks' `docker exec lys /lys …` lines stay valid. `golang.org/x/term` is already a dependency.
